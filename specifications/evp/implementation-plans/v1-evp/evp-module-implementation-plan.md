# Module evp : plan de réalisation

Sources : les six demandes à l'API du dossier `v1-evp` (`acces-auth`, `absences`, `creches`, `justificatifs`, `notifications-journal-export`, `sources`) et la demande d'origine « v1 : EVP, préparation et suivi des absences (Micro-Stars) ». Le socle est gelé : tout le code va dans de nouvelles fonctionnalités de `api/src/features/`. La provenance de chaque règle est reprise telle que la demande la porte.

### Réutilisation du socle (obligatoire, rien à redéfinir)
- Validation : `idParamsSchema`, `uuidList(min, max)`, `trimmedName`, `emailSchema`/`isValidEmail` (avec `.max(254)` et le suffixe de domaine ajoutés par le schéma EVP), `pageOf` ; les requêtes paginées dérivent de `paginationQuerySchema` avec un raffinement `size ∈ {10, 25, 50}` (jamais une seconde implémentation de `from`/`size`).
- Audit : `@Audited`/`@AuditExempt`, `normaliseSummary`, `fieldNames`, `count` de `platform/audit/audit-text.ts` pour construire les résumés ; le journal EVP lit `base.audit_logs` (`auditLogs` de `features/audit/audit.tables.ts`) et reprend le calcul des bornes de date de `AuditService.list` plutôt que de le réécrire.
- Périmètres : `ScopedRepository`, `declareScopedTable`, `runWithScopeAccess` ; synchronisation des groupes techniques par `features/groups/memberships.ts` (`lockMemberships`).
- Comptes : l'empreinte bcrypt du `credentials` de type `token` réutilise la fabrique de `features/users` (celle de l'import de comptes) ; ne pas dupliquer le hachage.
- Transactions : `ambientTransaction`/`transactionAware` ; aucune connexion ni transaction hors de `Database`.
- Studio : `useCall`, `usePagedList`, `AdminList`, `FormDialog`, `PageHeader`, `notify`, `safeRedirect`, `api.ts` de `studio/src/app/shared/` (voir « Réutilisation » de chaque plan d'écran).

## Données

Toutes les tables sont dans le schéma `base` (mécanisme `*.tables.ts` du socle). `data-contract.md` ne contient aucune de ces tables : il ne s'agit pas d'une modification de colonne contractée, mais l'ajout est signalé par dispute (voir « Litiges à ouvrir »). Horodatages `timestamptz` défaut `now()`, identifiants `uuid` défaut `gen_random_uuid()`. Une seule migration par lot (`pnpm migrate:gen && pnpm migrate:all`).

### Accès et crèches
- `evp_accounts` : `user_id` uuid PK → `base.users(id)` ; `name` text 1..120 ; `email` text unique (minuscules, ≤ 254, se termine par `@micro-stars.fr`) ; `role` enum `evp_role` (`DIRECTRICE`, `RO`, `RH`, `ADMINISTRATRICE`, `SUPERADMIN`) ; `active` bool ; `removed_at` timestamptz null ; `created_at`, `updated_at`. Le compte `base.users` associé porte le rôle socle `admin` pour SUPERADMIN, `user` sinon, et un identifiant de connexion Google sans mot de passe utilisable (`credentials` de type `token`, empreinte d'octets aléatoires, comme l'import de comptes). La ligne `evp_accounts` est la seule source des droits métier, relue à chaque requête.
- `creches` : `code` text PK 1..20, au format de code de périmètre du socle (`^[a-z0-9][a-z0-9_-]{0,49}$`, minuscules : la lecture Sheets normalise la casse ; un code hors format est écarté avec l'anomalie « Code de crèche invalide ») ; `name` text ; `siret` text unique ; `directrice_name` text null ; `directrice_email` text null ; `ro_names` text[] ; `verified` bool ; `source_read_id` uuid null ; `scope_code` text not null = `code`, référence `base.scopes(code)` `on delete restrict on update restrict`, table déclarée `declareScopedTable`.
- `creche_assignments` : `(user_id, creche_code)` PK, FK vers `evp_accounts` et `creches` ; index sur `creche_code`. Une DIRECTRICE ou une RO n'a de lignes que par ici. Vidé au retrait.
- Le périmètre « crèches » s'appuie sur le mécanisme de périmètre du socle : chaque crèche est un `base.scopes(code)` ; l'affectation d'un compte crée/retire son appartenance au groupe technique `evp:<code>` qui atteint ce périmètre (même transaction que `creche_assignments`, jamais éditable par les écrans du socle pour ces groupes). RH, ADMINISTRATRICE : consultation globale via le groupe technique `evp:all` (lié à tous les périmètres de crèche) ; SUPERADMIN : rôle socle `admin`. La lecture Sheets qui crée une crèche crée aussi son `base.scopes`, son groupe `evp:<code>` et sa liaison à `evp:all`, dans la même transaction (jamais de crèche sans périmètre). Invariant testé : `creche_assignments` ⇔ appartenances aux groupes `evp:<code>`. Un compte à consultation globale (RH, ADMINISTRATRICE, SUPERADMIN) satisfait la condition « au moins une crèche » par son périmètre `ALL`, même si le référentiel est vide. Les écritures de l'ADMINISTRATRICE sur les dossiers sont refusées par garde métier, non par le périmètre.

### Absences
- `absence_types` : `code` text PK (9 valeurs semées) ; `label` ; `expected_piece` text null ; `private_piece` bool ; `hr_review` bool ; `payfit_code` text null (code exporté et affiché) ; `payfit_compatible_codes` text[] (codes PayFit admissibles au rapprochement, contient `payfit_code`). Lecture seule, aucune route d'écriture (`rule-evp-declare-types-defaults`). La demande ne donne aucun code PayFit : le semis les laisse vides (affichés « Non configuré ») et un type sans code compatible ne peut jamais être confirmé (le dossier reste « à vérifier ») ; les tests posent les codes par SQL. Choix de réalisation à signaler à QA.
- `absences` : `id` ; `creche_code` (FK) ; `scope_code` (= crèche, `declareScopedTable`) ; `contract_id` uuid FK `payfit_contracts` ; `type_code` FK ; `start_date`, `end_date` date ; `start_half`, `end_half` enum `half_day` (`MATIN`, `APRES_MIDI`) ; `status` enum `absence_status` (`A_COMPLETER`, `ANTICIPEE`, `A_VALIDER`, `A_SAISIR`, `DANS_PAYFIT`, `REJETEE`, `ANNULEE`) ; `saisie_declaree` bool défaut false ; `comment` text null `check (char_length <= 500)` ; `payroll_month` char(7) ; `blockages` jsonb (liste `{code,message}` recalculée à chaque contrôle) ; `last_decision` jsonb null (`kind, by, at, reason`) ; `declared_by`, `declared_at` ; `created_at`, `updated_at`. Contraintes : `end_date >= start_date`, et si égalité `NOT (start_half = 'APRES_MIDI' AND end_half = 'MATIN')` (`rule-evp-declare-half-day-order`). Index unique partiel sur `(contract_id, type_code, start_date, start_half, end_date, end_half)` où `status in ('A_COMPLETER','ANTICIPEE','A_VALIDER','A_SAISIR','DANS_PAYFIT')` (doublon exact actif). Index `(creche_code, status)`, `(payroll_month, creche_code)`, `(created_at desc)`.
- `absence_events` : chronologie append-only (`absence_id`, `at`, `kind`, `text`, `by_user_id` null = Système, `payload` jsonb sans donnée médicale) ; triggers refusant `UPDATE`/`DELETE`, sur le modèle de `0001_audit_append_only`. Contient aussi l'événement de confirmation PayFit.
- `absence_pieces` : voir Justificatifs.
- `payfit_proofs` : `id`, `absence_id`, `observation_id`, `observed_at`, `company_id`, `siret`, `payfit_absence_id`, `code`, `source_status`, `superseded_by` null. Append-only ; la preuve antérieure n'est jamais effacée (`rule-evp-payfit-alerts`).
- `payfit_alerts` : `id`, `absence_id`, `kind` (`MODIFIEE`, `ANNULEE`, `DISPARUE`), `observed_at`, `change` text (administratif), `prior_proof_id`, `resolved_at` null.

- Config : correspondance type EVP → codes PayFit compatibles dans `absence_types.payfit_compatible_codes` ; statuts source admissibles en constante.

### Sécurité au niveau des lignes (base)
`rule-evp-rights-db-enforced` (user). En plus du filtre `scope_code` du socle, migration SQL manuelle : `ENABLE ROW LEVEL SECURITY` et `FORCE ROW LEVEL SECURITY` sur `absences`, `absence_pieces`, `absence_events`, `notifications`, `notification_reads` (ligne propre à `evp.user_id`), `closures`, `payfit_alerts`, `payfit_proofs`, avec politiques lisant `current_setting('evp.user_id')` et `current_setting('evp.scope_all')`. Politique de lecture : toutes les lignes si `scope_all`, sinon les lignes dont la crèche figure dans `creche_assignments` de l'appelant ; politique d'écriture : refus pour ADMINISTRATRICE.

**Le rôle de connexion `database` est SUPERUSER** (`.cuisine/bin/cuisine`, `cloud-setup.sh`) : un superutilisateur contourne la sécurité au niveau des lignes même avec `FORCE`. `FORCE` seul ne prouve donc rien. La migration crée donc un rôle `evp_app` (`NOLOGIN NOBYPASSRLS`, droits `SELECT/INSERT/UPDATE/DELETE` sur les tables du schéma `base` et ses séquences, privilèges par défaut pour les tables futures ; aucun droit `UPDATE/DELETE` sur `absence_events`, `closures`, `payfit_proofs`, en plus des déclencheurs). L'intercepteur de contrôleur des routes EVP (`@UseInterceptors`, donc à l'intérieur de l'intercepteur d'audit global) exécute, au début de la transaction de la requête, `SET LOCAL ROLE evp_app` puis `set_config('evp.user_id', …, true)` et `set_config('evp.scope_all', …, true)` ; sans transaction ambiante (route de lecture non tracée), il en ouvre une (`db.transaction` + `ambientTransaction.run`). Une requête EVP sans ce contexte ne lit aucune ligne (échec fermé : réglages absents ⇒ politique fausse). Les tâches internes (rapprochement, purge opportuniste) s'exécutent sans `SET ROLE` (rôle de connexion), uniquement dans une transaction ouverte par le service avec `runWithScopeAccess('full', …)`. Les tests SQL directs prouvent la RLS en faisant `SET LOCAL ROLE evp_app` + `set_config` dans une transaction (le rôle `database` seul ne la subit pas ; l'amorçage SQL de la recette reste fait avec lui).

## Opérations

Conventions communes : toutes les routes `GET` de lecture sont `@Access({ action, roles: ['user'] })` (admite `user` et `admin`) ; la restriction métier (capacité) est une garde `@UseGuards(CapabilityGuard('<capacité>'))` qui s'exécute avant la validation et avant toute recherche (régime `auth+custom` dans `cuisine:routes`). Les capacités sont relues en base à chaque requête (`EvpAccessService.load(req.user.id)` : compte actif, rôle, crèches) ; un compte retiré, inactif ou sans crèche reçoit `403 access.account_inactive` / `403 access.not_authorized` et la session n'est plus acceptée à la requête suivante (`rule-evp-rights-rechecked`). Tout `POST` est `@Audited` (objet « Absence », « Accès », « Justificatif », « Clôture », « Export », « Lecture de source ») ou `@AuditExempt('<raison>')`. Un intercepteur global du module pose `Cache-Control: no-store` (`rule-evp-no-store`). Tous les corps, requêtes et réponses sont des schémas Zod avec bornes (`.meta({ id })` pour les composants), `strictObject` sur les `PATCH`. Les identifiants de chemin passent par `idParamsSchema`. Les erreurs : `{ status, code, message }`, codes stables ci-dessous, jamais de SQL ni de chemin.

### service-status, google-sign-in, profile, settings
- `GET /service-status` : `@Public()`. Sortie `{ status: 'ready'|'unavailable', reason: 'google_not_configured'|'database_unreachable'|'maintenance'|null, message: string 0..300 }`. Attrape toute erreur de dépendance et répond `200 unavailable`, jamais `5xx`. Aucune donnée RH. Exemption d'audit non requise (lecture).
- `GET /google-sign-in/start` : `@Public()`. Query `redirection` (string 1..300, validée comme chemin relatif sûr, sinon ignorée : défaut `/`). Génère `state` signé (HMAC avec `COOKIE_SECRET`), lié au navigateur par un cookie court `HttpOnly SameSite=Lax`, et un PKCE ; `302` vers Google avec `hd=micro-stars.fr`, portées `openid email profile` seulement. `503 platform.service_unavailable` si les variables Google ne sont pas configurées. Exemption d'audit : `GET`, sans objet.
- `GET /google-sign-in/callback` : `@Public()`. Query `code` et `state` (1..2048), `error` facultatif. Vérifie `state` et PKCE, échange le code côté API, lit l'e-mail vérifié et le domaine ; applique les contrôles de `rule-evp-login-domain-not-enough` ; pose le cookie de session du socle (durée 8 h, voir ci-dessous) et répond `302` vers l'origine du studio (`/` ou le chemin sûr) ; sinon `302 /connexion?erreur=domaine|non_autorise|annule|echec`. Jamais de JSON. Compte absent, inactif ou sans crèche : même `non_autorise`. Un compte à consultation globale (RH, ADMINISTRATRICE, SUPERADMIN) satisfait « au moins une crèche » par son périmètre `ALL`. La connexion n'est pas journalisée : la demande ne le réclame pas et le socle exempte lui-même `POST /auth/login` (aucune donnée métier modifiée) ; pas d'écriture d'audit depuis un `GET`, pas de dispute. Aucun compte créé.
- Session 8 h (`rule-evp-session-8h`) : le `TokenService` du socle est gelé à 24 h (`SESSION_SECONDS`) ; le jeton de session EVP est donc émis avec une expiration de 8 h par un `EvpSessionService` propre (mêmes claims `sub` et `role`, signés avec `JWT_SECRET`, `exp` = 8 h, donc déjà refusé `401` par `SessionService.authenticate` sans changement du socle). Le cookie reprend `SessionService.cookieName(host)` et `cookieOptions(host)` avec `maxAge = 28 800 000 ms` (ne pas utiliser `setSessionCookie`, qui fixe 24 h). Le callback n'ayant ni `Origin` ni `Referer` du studio, `host` est celui de la première origine de `STUDIO_ORIGINS` (variable déjà validée par le socle) correspondant au `state` signé ; la redirection finale va vers cette origine. La garde `CapabilityGuard` refuse en plus tout jeton dont l'âge (`iat`) dépasse 8 h (un jeton de 24 h obtenu par `POST /auth/login`), `401 security.invalid_token`. Si le socle gelé s'y oppose : dispute.
- `POST /auth/login` du socle : conserve sa route ; pour un compte présent dans `evp_accounts`, il répond `401 security.invalid_credentials` (aucune session par mot de passe, `rule-evp-login-google-only`). Réalisé par un intercepteur du module EVP sur cette route sans modifier `features/auth/` ; sinon par la dispute « socle ». Les comptes EVP n'ont de toute façon aucun mot de passe utilisable.
- `GET /profile` : `@Access({ action: 'profile:read', roles: ['user'] })`. Sortie `{ id, name 1..120, email, role: enum 5 valeurs, active: true, scope: 'ASSIGNED'|'ALL', creches: [{ code, name }] (max 500, vide si ALL), capabilities: enum[] (constante partagée), sessionExpiresAt: date-heure }`. `403 access.account_inactive`, `403 access.not_authorized`.
- `GET /settings` : `@Access({ action: 'settings:read', roles: ['user'] })`. Sortie telle que demandée ; `limits` en constantes (8, 5, 60, 10485760, `PDF|JPEG|PNG`), `windows` textuels, `payfitWritesEnabled: false` en littéral. Aucun secret : le schéma de réponse est une liste blanche, testée.

### access
Capacité `access:manage:ro` (RH, ADMINISTRATRICE, SUPERADMIN) ; `access:manage:directrice` en plus pour SUPERADMIN. Création et rattachement des comptes : voir « Données » (`base.users`, `credentials`, groupes techniques) ; les groupes `evp:*` sont synchronisés par `features/groups/memberships.ts`.
- `GET /access-accounts` : `access:list`. Query `search` 1..100, `role` (`RO`|`DIRECTRICE`), `active` bool, `from` entier ≥ 0, `size` ∈ {10, 25, 50} (défaut 10), pagination du socle. Sortie `{ items: [{ id, name, email, role, active, creches: [{code,name}] }], total }`. Exclut les comptes privilégiés (`rule-evp-access-list-scope`). `403 access.role_not_manageable` pour un filtre de rôle non gérable par l'appelant.
- `POST /access-accounts` : `access:create`, audité (« Accès », résumé construit depuis la réponse et les noms de champs). Corps `{ email ≤ 254 en @micro-stars.fr, name 1..120, role RO|DIRECTRICE, active, crecheCodes string[0..50] (items 1..20) }`. Transaction : verrou, création de `base.users` + `evp_accounts` + affectations + appartenance de groupe. Erreurs : `400`, `403 access.role_not_manageable`, `409 access.email_already_exists`, `422 access.invalid_domain`, `422 access.creche_required` (actif sans crèche), `422 access.creche_not_verified` (crèche absente ou `verified = false`), `422 access.directrice_source_mismatch` (nom de la directrice différent de `creches.directrice_name` pour au moins une crèche).
- `PATCH /access-accounts/:id` : `access:update`, audité. Corps `strictObject { name?, role?, active?, crecheCodes? }`. `403 access.privileged_account`, `409 access.cannot_change_own_role`, `404 access.not_found`, mêmes `422`. Revalidation sous verrou `for no key update`.
- `POST /access-accounts/:id/remove` : `access:remove`, audité. Désactive, vide les affectations, pose `removed_at`, conserve l'historique, aucune suppression de ligne. `403 access.privileged_account`, `403 access.role_not_manageable` (directrice), `404 access.not_found`.

### creches et closures
- `GET /creches` : `creches:list`, tout compte EVP ; la liste suit le périmètre (directrice, RO : assignées ; autres : toutes). Sortie `{ items: [{ code, name, siret, directriceName|null, roNames: string[], verified }] }`.
- `GET /creches/:code/contracts` : `creches:contracts`, capacité `absences:create`, crèche du périmètre (`404` indiscernable hors périmètre). Query `search` 0..100, `size` 1..20 (défaut 20). Contrats de la société PayFit liée par SIRET unique ; aucun contrat si la liaison n'est pas unique. Sortie `{ items: [{ contractId, payfitContractId, employeeName, startDate, endDate|null }] }`.
- `GET /creches/:code/closures` : `closures:list`. Mois de paie courant et cinq précédents plus tout mois clôturé ; `openCount` calculé (états ouverts pour la crèche et le mois de paie). `404` hors périmètre.
- `POST /creches/:code/closures/:month` : `closures:attest`, la garde exige la capacité `absences:create` (directrice, RO, RH, superadmin ; ADMINISTRATRICE `403`, `rule-evp-closure-api-roles`) alors que la capacité exposée `closures:attest` (directrice seule) ne sert qu'à l'écran qui offre le bouton, audité (« Clôture »). Corps `{ attested: z.literal(true) }`. Transaction avec verrou consultatif par `(crèche, mois)` et recomptage des dossiers ouverts. `400` mois futur ou `attested` faux, `403`, `404`, `409 closures.open_absences` avec `details.openCount`, `409 closures.already_closed`.

### absences, todo
- `GET /absence-types` : `absences:types`. 9 éléments.
- `GET /todo` : `todo:read`. Query `crecheCode` ≤ 20, `from`, `to` (dates) ; `400 api.validation.incoming_failed` si `to < from`. Compteurs, 50 dossiers prioritaires au plus, 10 activités récentes.
- `GET /absences` : `absences:list`. Query `status` répétable (enum), `from`, `to`, `crecheCode`, `payrollMonth`, `open`. 200 éléments au plus, création décroissante, `truncated`.
- `GET /absences/:id` : `absences:get`. `404 repository.not_found` pour un dossier hors périmètre (via `ScopedRepository.get`).
- `GET /absences/:id/audit` : `absences:audit`, capacité `journal:read`. `403`, `404`.
- `POST /absences` : `absences:create`, capacité `absences:create`, audité (« Absence », sans commentaire dans le résumé). Corps conforme à la demande (`justificatifIds` 0..5 UUID distincts). `201` avec le dossier ; `200 { duplicate: true, absence }` pour un doublon exact actif (l'index unique partiel est le dernier rempart sous concurrence : capture de `23505` et relecture) ; `400`, `403` (ADMINISTRATRICE, crèche hors périmètre), `404 absences.contract_not_found`, `409 absences.creche_contract_mismatch` (le contrat existe mais n'appartient pas à la société liée à la crèche : refus à la création ; le même contrôle, rejoué plus tard, ne peut produire que le blocage `creche_contract_mismatch`, jamais une erreur HTTP), `409 absences.piece_not_attachable` (une pièce de `justificatifIds` est inconnue, non confirmée, déjà rattachée, d'une autre crèche, ou d'un autre déposant que l'appelant sans capacité sur la crèche : un seul code, indiscernable).
- `PATCH /absences/:id` : `absences:update`, capacité `absences:create` dans le périmètre (`rule-evp-declare-edit-server`). Modification côté serveur d'un dossier non terminé, **sans écran** (pas de formulaire général d'édition). Corps `strictObject` : `typeCode?`, `startDate?`, `startHalf?`, `endDate?`, `endHalf?`, `comment?` (0..500, `null` pour l'effacer), même refinement de demi-journée que la création, au moins un champ ; crèche et contrat ne changent jamais (un autre contrat est un autre dossier). États modifiables : `A_COMPLETER`, `ANTICIPEE`, `A_VALIDER`, `A_SAISIR` (tout sauf `DANS_PAYFIT`, `REJETEE`, `ANNULEE` : `409 absences.decision_not_allowed`). Sous verrou de la ligne, les contrôles sont rejoués et l'état recalculé comme à la création (une modification d'un dossier `A_SAISIR` le renvoie donc à `A_VALIDER`/`ANTICIPEE`/`A_COMPLETER` et remet `saisie_declaree` à faux) ; `payroll_month` est recalculé avec la date de création d'origine. Un résultat qui duplique un autre dossier actif exact donne `409 absences.duplicate_active` (capture de `23505`). `200 AbsenceDetail`, `404` hors périmètre, `403` (ADMINISTRATRICE), audité (« Absence », noms des champs envoyés, jamais le commentaire), événement de chronologie « Dossier modifié » (sans valeurs). Aucun `allowedActions` ne l'expose au studio. Le `200` doublon ne modifie aucune donnée : il est tracé comme toute réponse 2xx d'une route tracée (résumé « Déclaration déjà enregistrée »), sans nouvel événement de chronologie.
- `POST /absences/:id/submit` : `absences:submit`. `200` ; `409 absences.decision_not_allowed` (états autorisés : `A_COMPLETER`, `ANTICIPEE`, `A_VALIDER`).
- `POST /absences/validate-batch` : `absences:validate`, capacité `absences:decide`. Corps `{ absenceIds: uuid[1..50] distincts }`. Pour chaque id, sa propre transaction (verrou de la ligne, rejeu des contrôles). Une seule entrée d'audit en lot (compte) plus la trace de chaque décision dans `absence_events`. Réponse `{ validated: [{id}], blocked: [{ id, employeeName, blockages }] }`. Un id inconnu ou hors périmètre est `blocked` avec le blocage `absence_not_found`, indiscernable.
- `POST /absences/:id/validate` : `absences:validate`, `absences:decide`. `200` (`A_SAISIR`) ; `409 absences.validation_blocked` avec `details.blockages` ; `409 absences.decision_not_allowed` ; `403`.
- `POST /absences/:id/return` (`A_COMPLETER`), `POST /absences/:id/reject` (`REJETEE`) : corps `{ reason: string 1..500 }`, capacité `absences:decide`. États autorisés : `A_VALIDER`, `ANTICIPEE`, `A_SAISIR` pour le retour ; `A_COMPLETER`, `ANTICIPEE`, `A_VALIDER`, `A_SAISIR` pour le refus.
- `POST /absences/:id/cancel` : `absences:cancel`, motif 1..500, selon statut et périmètre : déclarants du périmètre sur `A_COMPLETER`, `ANTICIPEE`, `A_VALIDER` ; RH aussi sur `A_SAISIR` ; jamais sur `DANS_PAYFIT`, `REJETEE`, `ANNULEE` (`409 absences.decision_not_allowed`). ADMINISTRATRICE `403`.
- `POST /absences/:id/mark-entered` : `absences:mark-entered`, capacité `absences:decide`. Valable en `A_SAISIR` seulement ; passe `saisie_declaree` à vrai, état inchangé ; idempotent.
- Aucune route ne produit `DANS_PAYFIT` (`rule-evp-payfit-no-manual-confirm`), pas même `PATCH`. Aucun passage automatique de `ANTICIPEE` à `A_VALIDER` au jour J (aucune tâche planifiée, `rule-evp-declare-no-auto-anticipation`) : seule une soumission ou une modification rejoue les contrôles.

#### Table des transitions (source unique, `absences.transitions.ts` ; les plans d'écran s'y réfèrent)
| Décision | États de départ | Qui | État d'arrivée |
|---|---|---|---|
| `submit` | `A_COMPLETER`, `ANTICIPEE`, `A_VALIDER` | déclarants du périmètre (capacité `absences:create`) | recalculé par les contrôles |
| `validate` | `A_VALIDER` | RH (`absences:decide`) | `A_SAISIR` |
| `return` | `ANTICIPEE`, `A_VALIDER`, `A_SAISIR` | RH | `A_COMPLETER` |
| `reject` | `A_COMPLETER`, `ANTICIPEE`, `A_VALIDER`, `A_SAISIR` | RH | `REJETEE` |
| `cancel` | `A_COMPLETER`, `ANTICIPEE`, `A_VALIDER` ; `A_SAISIR` pour RH seulement | déclarants du périmètre ; RH | `ANNULEE` |
| `mark-entered` | `A_SAISIR` | RH | inchangé (`saisie_declaree` vrai) |
| `PATCH` | tous sauf `DANS_PAYFIT`, `REJETEE`, `ANNULEE` | déclarants du périmètre | recalculé |
Toute autre combinaison : `409 absences.decision_not_allowed`. `allowedActions` est calculé depuis cette table et la capacité de l'appelant ; `ATTACH` est proposé aux déclarants du périmètre tant que l'état n'est ni `DANS_PAYFIT`, ni `REJETEE`, ni `ANNULEE`. `JournalEntry` (réponse de `GET /absences/:id/audit`) a la même forme qu'un élément de `GET /journal-entries`.
- Toutes les routes d'écriture sur un dossier verrouillent la ligne `absences` (`for update`), rejouent les contrôles, écrivent `absence_events` et l'entrée d'audit dans la transaction du socle (`rule-evp-audit-atomic`).

#### Contrôles rejoués (service `AbsenceChecksService`)
Retourne une liste ordonnée de blocages `{ code, message }` : `creche_contract_mismatch`, `outside_contract_period`, `overlap_evp` (autre dossier actif du même contrat), `overlap_payfit` (observation PayFit sur la période, hors la preuve du dossier lui-même), `piece_missing` (type exigeant une pièce sans pièce confirmée), `piece_not_confirmed`. Statut calculé : un blocage donne `A_COMPLETER`, sinon début après le jour courant Europe/Paris donne `ANTICIPEE`, sinon `A_VALIDER`. `nextAction` : `DECLARANT` si `A_COMPLETER`/`ANTICIPEE`, `RH` si `A_VALIDER` ou alerte PayFit non résolue, `LECTURE_PAYFIT` si `A_SAISIR`, `AUCUN` sinon. `allowedActions` est calculé ici et est la seule source pour le studio. Mois de paie : fonction pure `payrollMonth(start, createdAt)` dans `evp-core`.

### justificatifs
Le stockage est derrière une interface `ObjectStorage` (`presignPut`, `head`, `readRange`, `copy`, `delete`, `presignGet`) avec une implémentation S3-compatible configurée par l'environnement et un double de test (voir « Doubles de test »). Les octets ne passent jamais par l'API ni la base en production.
- `POST /justificatifs/authorize-upload` : `justificatifs:authorize`, capacité `absences:create`, crèche du périmètre. Corps `{ crecheCode 1..20, absenceId?, fileName 1..255, contentType enum, sizeBytes int 1..10485760 }`. Crée la ligne `AUTHORIZED`, signe un `PUT` valable 5 minutes lié au type et à la taille. `201 { id, uploadUrl, method:'PUT', headers, expiresAt }`. `400`, `403`, `404`. Audité (« Justificatif », sans nom de fichier dans le résumé).
- `POST /justificatifs/:id/confirm` : `justificatifs:confirm`, déposant ou capacité sur la crèche. Contrôle `head` (taille réelle = annoncée et ≤ 10 485 760), signature de format lue sur les premiers octets (`%PDF-`, `FF D8 FF`, `89 50 4E 47 0D 0A 1A 0A`), délai de 5 minutes, puis copie vers `final_key`, suppression du dépôt, `CONFIRMED`, rattachement si `absenceId` avec rejeu des contrôles. `200 { id, name, sizeBytes, confirmed: true }` ; deuxième confirmation : `200` idempotent ; `409 justificatifs.not_uploaded | size_mismatch | signature_mismatch | upload_expired | too_many` ; `403` ; `404`. Un échec de contrôle supprime l'objet déposé.
- `POST /justificatifs/:id/read-link` : `justificatifs:read-link`. `200 { url, expiresAt }` (60 s) ; `403 justificatifs.private_piece` ; `404` ; `409 justificatifs.not_confirmed`. Audité « Ouverture de justificatif » (dossier, auteur, jamais le nom d'une pièce privée) dans la même transaction que l'émission du lien.
- `PieceCleanupService` (`rule-evp-piece-unattached-cleanup`) : supprime du stockage, puis passe à `PURGED`, les pièces confirmées non rattachées de plus de 24 h et les dépôts expirés (50 au plus par passage). Aucun minuteur ni ordonnanceur : le passage est opportuniste, exécuté après `POST /justificatifs/authorize-upload` (hors de la transaction de la requête), avec `runWithScopeAccess('full', …)` et sans `SET ROLE`. Ce choix évite toute planification (la demande n'en veut aucune) et rend la règle testable (le test antidate des lignes par SQL, puis appelle `authorize-upload`).

- `GET /notifications/unread-count` : `notifications:count`.

### journal et exports
- `GET /journal-entries` et `GET /journal-entries/filters` : `journal:list`, `journal:filters`, capacité `journal:read`. Lecture de `base.audit_logs` (socle inchangé) restreinte à une liste blanche d'actions EVP (`absences:*`, `access:*`, `closures:attest`, `justificatifs:*`, `exports:absences`, `sources:refresh*` ; jamais les actions du socle), avec joins sur `evp_accounts` pour `actorName` (« Système » pour l'identifiant réservé ci-dessous) et libellé français de l'opération déduit du code d'action (`operation` = code d'action de `@Access`, table codes → libellés dans `journal.labels.ts`). `absenceId` : `object_id` quand `object_type` vaut « Absence » ou « Justificatif » (pour une ouverture de pièce, l'`objectId` du descripteur est l'identifiant du dossier, pour une validation en lot c'est « lot » et `absenceId` reste nul). Entrées automatiques du rapprochement : écrites directement dans `audit_logs` par `ReconciliationService` (action `sources:reconcile`, libellé « Rapprochement PayFit ») avec l'identifiant d'acteur réservé `00000000-0000-0000-0000-000000000000` et l'e-mail `systeme@evp.invalid` (la colonne `actor_id` n'a pas de clé étrangère). Pagination `from`/`size ∈ {10,25,50}` défaut 25, ordre `occurred_at desc, id desc`. Aucun nom de fichier de pièce privée ni valeur brute (les résumés sont déjà construits ainsi à l'écriture).
- `POST /exports/absences` : `exports:absences`, capacité `export:run`. Corps `{ from, to }` avec `to ≥ from` et au plus 366 jours (refinement documenté dans le contrat). `200 text/csv; charset=utf-8`, `Content-Disposition: attachment; filename="absences-AAAA-MM-JJ_AAAA-MM-JJ.csv"`, déclaré dans `@ApiRoute` avec le type `text/csv` et un schéma `string`. Chevauchement : `start_date <= to AND end_date >= from`. Audité (« Export », période et nombre de lignes, aucun nom). Le CSV est produit en flux depuis une requête curseur, dans la même transaction que l'audit.

### sources
Connecteurs derrière des interfaces `WorkspaceConnector`, `SheetsConnector`, `PayfitConnector`, `AqoonaConnector` (lecture seule : aucune méthode d'écriture n'existe dans l'interface), avec des doubles de test pour la recette (voir « Doubles de test »). Identifiants en configuration (`api/.env.template` : variables ajoutées, validées par Zod, jamais exposées). Le gabarit fixe `EVP_SOURCES_DRIVER=fake` et `EVP_STORAGE_DRIVER=fake` : le pilote réel exige ses identifiants et l'API refuse de démarrer s'ils manquent ; `/service-status` répond `google_not_configured` tant que les variables Google sont vides.
- `GET /sources` : `sources:list`, capacité `sources:read`. Un élément par source (`workspace`, `sheets`, `payfit`, `aqoona`) avec état, dernière lecture, fenêtre, volumes, `anomalyCount`, `canRefresh` (selon la capacité de l'appelant) et `currentRunId`.
- `POST /sources/:key/refresh` : `sources:refresh`, `key` ∈ `sheets|payfit|aqoona`. La garde exige `sources:refresh:<key>`. `202 { runId, state:'RUNNING' }` ; `404` pour `workspace` ; `409 sources.run_in_progress` (index unique partiel). Audité « Lecture de source ». Le traitement s'exécute après la réponse dans une tâche interne qui met à jour `source_runs`.
- `POST /sources/refresh-all` : `sources:refresh-all`, SUPERADMIN (`sources:refresh:sheets`). Enchaîne `sheets`, `payfit`, `aqoona` ; `202 { runId, steps }` ; `409` si l'une des trois sources est déjà en lecture. Une étape en échec arrête l'enchaînement (run `FAILED`, étapes suivantes non lues, message sans détail technique) : choix de réalisation, la demande ne le précise pas.
- `GET /sources/runs/:id` : `sources:run`, `sources:read`. `404`.
- `GET /sources/:key/anomalies` : `sources:anomalies`, `sources:read`. Pagination `from`/`size ∈ {10,25,50}`.
- Lecture Sheets (onglet « Contacts des crèches » : nom, code, SIRET, adresse de connexion, nom de la directrice, nom et e-mail RO) : upsert du référentiel `creches` avec création du périmètre associé (voir « Données ») ; sans jamais toucher `evp_accounts` ni `creche_assignments`, ni réactiver une RO retirée ; recalcul de `verified` ; anomalies « Écart RO », « RO retirée présente dans le tableau », « SIRET manquant ou invalide », « Code de crèche invalide » et, pour confirmer les affectations des directrices, « Directrice différente du tableau » quand une directrice affectée ne correspond plus au `directrice_name` de sa crèche (anomalie seulement, aucune modification de compte). Lecture PayFit : fenêtre début de M−2 à fin de M+2 en Europe/Paris, upsert des sociétés, collaboratrices, contrats, absences, observations ; puis rapprochement (service `ReconciliationService`) dans une transaction par dossier. Lecture Aqoona : fenêtre J−28 à J+35, stockage du planning, appariement (nom de crèche normalisé : minuscules, sans accents ni ponctuation, espaces réduits ; puis prénom et nom dans cette crèche, rattaché si la correspondance est unique, sinon ligne non rattachée et anomalie), écartement des matricules NIR, aucun signal d'absence. Un matricule « ressemblant à un NIR » = après retrait des espaces, points et tirets, 13 chiffres (ou `2A`/`2B` en position 6-7) commençant par 1 ou 2, éventuellement suivis de 2 chiffres de clé ; la valeur n'est ni stockée, ni journalisée, ni mise en anomalie (seul `nir_discarded` est incrémenté) et la ligne est appariée par prénom et nom.
- Rapprochement : candidats = dossiers `A_SAISIR` (et `DANS_PAYFIT` pour les alertes). Confirmation seulement si exactement une observation fraîche (de la lecture en cours), même société et SIRET, même contrat, code compatible avec `absence_types`, mêmes dates et demi-journées, statut source admissible ; dans une transaction unique : `payfit_proofs`, `absence_events` (confirmation), passage à `DANS_PAYFIT`, `notifications` (kind `CONFIRMATION`), entrée d'audit de l'acteur « Système ». Sinon le dossier reste `A_SAISIR` avec blocage informatif « à vérifier ». Pour `DANS_PAYFIT` : dates/code changés → alerte `MODIFIEE` ; statut annulé → `ANNULEE` ; absence non retrouvée et `source_read_coverage.exhaustive` couvrant période et société → `DISPARUE` ; retrouvée à l'identique après alerte → événement et notification `RESTAURATION`, sans nouvelle preuve de confirmation. L'état du dossier n'est pas modifié par une alerte ; la preuve antérieure est conservée.

## Doubles de test, horloge et couverture

L'API de test tourne dans un autre processus que Jest : les doubles ne peuvent pas être des objets injectés par le test.
- Connecteurs (`EVP_SOURCES_DRIVER=fake`) : lisent des fixtures JSON (`api/.evp-fixtures-test/{workspace,sheets,payfit,aqoona}.json`, git-ignoré) que le test écrit avant de lancer la lecture ; ils journalisent chaque appel dans `calls.log` (preuve qu'aucune méthode d'écriture n'est appelée, par exemple à la validation et à l'export).
- Stockage (`EVP_STORAGE_DRIVER=fake`) : répertoire local `api/.evp-storage-test/` ; les URL signées pointent vers deux routes cachées du contrat (`@ApiRoute({ hidden: true })`) montées seulement quand le pilote est `fake` et refusées en production : `PUT` (vérifie l'expiration, le type et la taille signés) et `GET` (60 s). Le test inspecte le répertoire pour vérifier la copie hors dépôt, la suppression et l'absence d'objet après un échec de confirmation.
- Horloge : pas de faux temps côté serveur. Les tests antidatent par SQL (`upload_expires_at`, `created_at` des pièces) et forgent des jetons avec `JWT_SECRET` de `api/.env.test` (`iat` de 9 h pour l'expiration de session). `payrollMonth(start, createdAt)`, pure, a un test unitaire direct sur le 25 inclus, le 26, le début en mois futur et le changement d'année.
- Couverture des règles : un test de méta-contrôle lit ce plan et les demandes, extrait les identifiants `rule-evp-*` et échoue si l'un d'eux n'apparaît dans aucun titre de test ou, pour les règles d'écran, dans la liste des règles laissées aux tests de navigateur de QA (`acceptance/e2e/`).
