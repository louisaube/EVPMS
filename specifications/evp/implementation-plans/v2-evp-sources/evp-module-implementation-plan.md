# Module evp : plan de réalisation (v2-evp-sources)

Sources : les deux demandes à l'API de ce dossier (`google-sign-in-api-modification-request.md`, `sources-api-modification-request.md`), les plans d'écran `connexion` et `sources`, et la demande d'origine « v2 : EVP, connexion Google et lectures des sources externes ». Le socle est gelé ; tout le code va dans des fonctionnalités EVP non gelées : `google-sign-in/`, `sources/`, `service-status/`, `evp-core/`, et, pour de petites retouches listées ci-dessous, `access/` (colonne `google_sub`), `absences/` (`absence-checks.ts`) et `settings/` (`settings.service.ts`). La provenance de chaque règle est reprise telle que la demande la porte ; les règles ajoutées par le backend pour réaliser une règle amont sont marquées `(inferred)` et « backend ».

Aucune route nouvelle (decision D-0005, option A de Q-EVP-01) : la matrice `permissions.yaml` ne bouge pas. Une réponse change de forme (`GET /sources`), des tables EVP gagnent des colonnes.

## Réutilisation de l'existant (à lire avant d'écrire)
La v1 a déjà : `SourceConnectors` (classe abstraite : `listContacts`, `listPayfit`, `listPlannings`) avec `FixtureSourceConnectors` et `UnconfiguredSourceConnectors` dans `sources/source-connectors.ts` ; `SourceReaders` (`applySheets`, `applyPayfit`, `applyAqoona`, `normalise`, `NIR_PATTERN`, filtre de fenêtre Aqoona, anomalies `replaceAnomalies`) dans `sources/source-readers.ts` ; `payfitWindow()` et `aqoonaWindow()` dans `sources.service.ts` (fuseau `Europe/Paris`, via `evp-core/payroll-month.ts`) ; `ReconciliationService` ; `evpConfig()` ; le cookie de flux signé et `safeRedirection` de `google-sign-in.service.ts` ; `GET /service-status`, dont l'énumération `reason` contient déjà `google_not_configured`. La v2 **étend** ces éléments et n'en recrée aucun : pas de second `normalise`, de second filtre de fenêtre, de second calcul de fenêtre PayFit/Aqoona, de seconde détection de NIR, de second cookie de flux. Le nom `source-readers.ts` désignant déjà le code qui applique une lecture en base, les nouveaux appels HTTP s'appellent `*.client.ts` (et non `*.reader.ts`).

Tout dans le schéma `base`, fichiers `*.tables.ts` de la fonctionnalité concernée. Une migration (`pnpm migrate:gen && pnpm migrate:all`). Aucune colonne contractée de `data-contract.md` n'est touchée ; les ajouts sont signalés par dispute (voir « Litiges à ouvrir »).

Les comptes existants restent non liés ; la liaison se fait à la première connexion valide (`rule-evp-google-sub-binding`).
- `payfit_companies` : ajout `key_fingerprint` text null (SHA-256 hexadécimal de la clé API de l'entrée de configuration, jamais la clé) et `company_id_resolved_at` timestamptz null. `id` reste le `company_id` renvoyé par l'introspection. Sert à `rule-evp-payfit-company-id` : pas de nouvel appel d'introspection tant que l'empreinte est inchangée (backend, inferred). Le SIRET reste non unique.
- `payfit_contracts` : ajout `status` text not null défaut `ACTIVE` avec contrôle `in ('ACTIVE','ARCHIVED','PENDING')` (`rule-evp-payfit-contracts-all-statuses`).
- `payfit_absences` : `start_half` et `end_half` deviennent nullables (`rule-evp-payfit-half-day-mapping`, combinaison non interprétable) ; ajout `start_moment` et `end_moment` text null (valeur brute `beginning-of-day`, `middle-of-day`, `end-of-day`) pour que l'interprétation soit rejouable si la correspondance des demi-journées (decision D-0006) change. `status` reçoit la valeur brute de PayFit (`approved`, `pending_approval`, `declined`, `cancelled`, `pending_cancellation`). **Aucune migration des valeurs existantes** : la suite de recette de la v1 (`acceptance/evp-helpers.ts`, `PF`) sème et attend `VALIDATED`, `CANCELED`, `PENDING` (y compris `payfit_proofs.source_status = 'VALIDATED'`) et elle tourne sous `EVP_SOURCES_DRIVER=fake` (decision D-0003) ; les deux vocabulaires coexistent donc et `normalisePayfitStatus()` les rapproche à la lecture (backend, inferred).
- `payfit_coverage` : une ligne par société au lieu d'une ligne unique : clé primaire `company_id` (text) ; l'ancienne ligne unique (`id = 1`) est supprimée par la migration puis recréée à la lecture suivante. Ajout `reachable` bool. Nécessaire à `rule-evp-sources-partial-failure` (decision D-0007) : une société en échec garde sa ligne précédente avec `reachable = false` et `exhaustive = false`, ce qui supprime ses alertes de disparition. Colonne `exhaustive` conservée. `ReconciliationService.run()` et `compare()` reçoivent la couverture de la société de la preuve (`proof.company_id`) au lieu d'une couverture unique ; une société sans ligne de couverture est traitée comme non exhaustive. `applyPayfit` ne supprime les absences non revues (`observed_at < readAt`) que pour les sociétés lues, accessibles et exhaustives, avec un filtre sur `company_id`.
- `source_runs` (table des lectures de `sources.tables.ts`) : ajout `error_code` text null (un des cinq codes `sources.*`) et `partial` bool not null défaut false (vrai pour une lecture `SUCCEEDED` dont au moins une société ou adresse a échoué : c'est elle qui fait afficher l'état `PARTIAL`, decision D-0007). `error_message` garde les 1..200 caractères sans secret. `lastError` de `GET /sources` est lu sur la dernière lecture terminée de la source si elle est `FAILED` (`at` = `finished_at`), sinon `null`.
- `source_anomalies` : aucun changement de colonne ; nouveaux `type` (voir Règles).
- `aqoona_plannings` : ajout `address_label` text null (libellé non secret de l'adresse d'origine, 1..100) pour conserver les plannings d'une adresse en échec lors d'une lecture partielle (decision D-0007, backend, inferred). `aqoona_mismatches` : inchangé.

## Configuration

Les variables du tableau des deux demandes sont lues par `evp-config.ts` et listées en commentaires dans `api/.env.template` (noms seulement, aucune valeur). `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` et `GOOGLE_PUBLIC_ORIGIN` n'ont plus de valeur de substitution hors production (`rule-evp-google-endpoints-configurable`, demande Compatibilité). `PAYFIT_API_KEYS`, `AQOONA_URLS` et `SHEETS_PRIVATE_KEY` sont analysés au démarrage de la lecture, jamais à l'import, et une erreur d'analyse donne `sources.not_configured` sans citer la valeur. `api/.env.test` (écrit par la cuisine) doit fournir les variables pointant vers les serveurs factices quand l'API de test sert les tests de la v2 avec `EVP_SOURCES_DRIVER=real` ; les tests de la v1 tournent dans une autre API de test lancée avec `EVP_SOURCES_DRIVER=fake` (decision D-0003).

**Serveurs factices et processus séparé.** L'API de test est un processus distinct des tests : ses variables sont fixées à son démarrage et un test ne peut pas lui passer l'adresse d'un serveur factice qu'il démarre. Les serveurs factices écoutent donc sur des adresses locales **fixes**, déclarées dans `api/.env.test` (`GOOGLE_AUTH_URL`, `GOOGLE_TOKEN_URL`, `GOOGLE_CERTS_URL`, `SHEETS_BASE_URL`, `SHEETS_TOKEN_URL`, `PAYFIT_BASE_URL`, `PAYFIT_INTROSPECT_URL`) et dans `AQOONA_URLS` / `PAYFIT_API_KEYS` / `SHEETS_PRIVATE_KEY` (valeurs de test factices, jamais de vraie clé). Les valeurs de configuration sont lues à chaque lecture (`evpConfig()` n'est pas figé à l'import), mais les variables d'environnement ne changent pas pendant la vie du processus : un test fait varier le comportement du serveur factice (statuts, corps, délais), pas la configuration. Les cas « variable absente » (`google_not_configured`, `sources.not_configured`, JSON de clés illisible) se jouent donc soit en tests unitaires de `evp-config.ts` et des clients, soit dans une API de test supplémentaire lancée sans la variable (comme pour le pilote `fake`) ; le plan de test le distingue. `api/.env.template` ne porte que les noms, en commentaire ; l'écriture de `api/.env.test` appartient à la cuisine.

## Règles

### Connexion Google
- `rule-evp-google-token-verified-server` (user) : la session n'est ouverte qu'après `verify()` ; l'appel du vérificateur précède toute lecture de `evp_accounts`.
- `rule-evp-google-signature` (user) : `google-id-token.verifier.ts`, algorithme imposé RS256 (l'en-tête `alg` du jeton n'est pas obéi : `none` et HS256 sont refusés), clé choisie par `kid`.
- `rule-evp-google-certs-cache` (user ; repli sans `max-age` : inferred) : cache mémoire des clés avec expiration d'après `Cache-Control: max-age`.
- `rule-evp-google-certs-rotation` (inferred) : `kid` inconnu → une relecture, au plus une relecture forcée par minute.
- `rule-evp-google-certs-fail-closed` (inferred) : clés illisibles ou injoignables → `erreur=echec`, cache expiré non réutilisé.
- `rule-evp-google-aud`, `rule-evp-google-iss`, `rule-evp-google-hd`, `rule-evp-google-email-verified` (user) : contrôles séparés dans le vérificateur, chacun testé isolément ; `hd` comparé par le code lui-même à `GOOGLE_ALLOWED_DOMAIN` (comparaison stricte, insensible à la casse), jeton sans `hd` refusé comme `domaine`.
- `rule-evp-google-exp` (user ; tolérance de 60 s : inferred) : horloge du serveur.
- `rule-evp-google-domain-configurable`, `rule-evp-google-endpoints-configurable` (user) : `GOOGLE_ALLOWED_DOMAIN`, `GOOGLE_AUTH_URL`, `GOOGLE_TOKEN_URL`, `GOOGLE_CERTS_URL`.
- `rule-evp-google-flow-redirect` (inferred, decision D-0005) : cookie signé de 10 minutes portant `state`, `nonce`, vérificateur PKCE ; `nonce` du jeton comparé à celui du cookie ; le jeton vient de la réponse de `GOOGLE_TOKEN_URL`, jamais du navigateur.
- `rule-evp-google-sub-identity`, `rule-evp-google-sub-binding`, `rule-evp-google-sub-mismatch` (inferred, decision D-0008), `rule-evp-google-sub-email-change`, `rule-evp-google-sub-unique` (inferred sauf la première) : service de connexion ; la liaison et la création du compte dans une transaction avec verrou sur la ligne du compte pour que deux connexions simultanées ne lient qu'un `sub` ; violation d'unicité → `non_autorise`.
- `rule-evp-login-domain-not-enough`, `rule-evp-login-single-denial`, `rule-evp-session-8h` (inchangés) : non retouchés.
- `rule-evp-google-error-causes` (inferred) : fonction unique `toLoginError(cause)` construisant la table ; un délai de 10 s sur l'échange du code et la lecture des clés.
- `rule-evp-google-scopes-minimal` (inferred, inchangé) : `openid email profile`.
- `rule-evp-google-sign-in-audit` (inferred) : audit « Liaison Google enregistrée », sans `sub`.
- `rule-evp-secrets-never-exposed` (user) : voir ci-dessous « Secrets ».

### Secrets (commun aux deux demandes)
- `rule-evp-secrets-never-exposed` (user) : `redactSecrets(text)` remplace par `[masqué]` toute valeur de secret connue de la configuration (secret client, clé privée, clés PayFit, adresses Aqoona complètes, jetons d'accès en mémoire) et toute chaîne `?…` d'une adresse ; appliqué à chaque message avant journalisation, stockage (`error_message`, anomalies, audit) et réponse. Les exceptions des clients HTTP sont reconstruites (code + source), jamais relayées telles quelles (backend, inferred). Les journaux applicatifs ne consignent ni en-têtes `Authorization` ni corps de requête ni adresse complète.

### Sources, commun
- `rule-evp-sources-readonly` (user, inchangé) : les clients HTTP n'exposent que `get` et, pour l'obtention d'un accès, `postForm`/`postJson` aux deux seules adresses d'accès ; test statique : aucun `PUT`, `PATCH`, `DELETE`.
- `rule-evp-sources-configurable` (user ; interrupteur unique : inferred, decision D-0003) : aucune adresse en dur hors valeurs par défaut officielles ; un seul `EVP_SOURCES_DRIVER` pour tout le processus, sans repli par source sur les fixtures.
- `rule-evp-sources-failure-state` (user) : la lecture s'exécute en mémoire puis copie en une transaction ; un échec global ne laisse rien de copié et ne change pas `lastReadAt` (l'échec d'une société ou d'une adresse parmi d'autres relève de `rule-evp-sources-partial-failure`).
- `rule-evp-sources-error-codes` (inferred), `rule-evp-sources-timeouts` (inferred), `rule-evp-sources-run-single` (inferred, inchangé), `rule-evp-sources-refresh-audited` (inferred, inchangé), `rule-evp-sources-no-scheduler` (user) : classement dans `http-client.ts` ; aucune tâche planifiée créée.
- `rule-evp-sources-partial-failure` (inferred, decision D-0007) : lecture partielle. Chaque société (ou adresse) est lue en mémoire séparément ; celles qui répondent sont copiées en une transaction, celles en échec gardent leurs données précédentes (`payfit_coverage.reachable = false`, `exhaustive = false`, pas d'alerte de disparition) et créent l'anomalie `payfit_company_unreachable` (ou `aqoona_address_unreachable`) ; run `SUCCEEDED` et source `PARTIAL`, `lastError` nul. Toutes en échec, ou échec global de configuration : run `FAILED`, rien de copié (`rule-evp-sources-failure-state`).
- `rule-evp-sources-manual` (user, inchangé), `rule-evp-sources-sheets-superadmin` (user, inchangé) : capacités existantes.

### PayFit
- `rule-evp-payfit-bearer`, `rule-evp-payfit-company-id`, `rule-evp-payfit-scopes` (user) : l'introspection est faite avec la clé en Bearer et `{"token": clé}` ; les portées ne sont jamais demandées par le code (elles sont attachées à la clé) mais un `403` est classé « Portée PayFit manquante » ; aucun appel d'écriture.
- `rule-evp-payfit-company`, `rule-evp-payfit-collaborators`, `rule-evp-payfit-contracts`, `rule-evp-payfit-absences` (user) : chemins exacts de la demande ; `identificationNumber` et jamais `siret`.
- `rule-evp-payfit-siret-check` (inferred), `rule-evp-payfit-contracts-all-statuses` (inferred) : le statut du contrat est conservé mais ne filtre rien dans le sélecteur de contrats (`creches.service.ts`) ni à la déclaration (`absences.service.ts`) : la période du contrat fait foi (blocage `outside_contract_period` existant). Ces fichiers ne sont pas modifiés.
- Nom de la société (`payfit_companies.name`) : champ `name` de `GET /companies-fr/{companyId}` s'il est une chaîne non vide, sinon le SIRET (backend, inferred ; le nom exact du champ n'est pas donné par la demande et un champ absent ne doit pas faire échouer la lecture).
- `rule-evp-payfit-window` (user) : bornes calculées dans le fuseau `Europe/Paris` à partir de la date du jour (backend, inferred).
- `rule-evp-payfit-status-all` (user) : `status=all` à chaque appel d'absences.
- `rule-evp-payfit-status-admissible`, `rule-evp-payfit-status-alerts` (inferred), `rule-evp-payfit-pending-cancellation` (inferred, decision D-0002) : dans `reconciliation.service.ts`, sur le statut passé par `normalisePayfitStatus()`. `confirm()` ne retient que `approved` (aujourd'hui `eq(status, 'VALIDATED')`) ; `compare()` : `cancelled`/`declined` → `ANNULEE`, `pending_approval` → `MODIFIEE`. **`pending_cancellation` doit être traité avant la comparaison générique des champs** : sans cela la branche existante `observation.status !== proof.sourceStatus` lèverait une alerte `MODIFIEE`. Dans ce cas `compare()` ne crée aucune alerte, ne résout pas une alerte ouverte et rend la main. `proof.sourceStatus` est comparé après normalisation des deux côtés (une preuve v1 `VALIDATED` face à une lecture `approved` n'est pas une modification).

## Tests

Jest dans `api/src/features/<feature>/tests/`, API de test via `@evpms/api-client`, amorçage SQL, `truncate` en `beforeEach`. Les services externes sont des serveurs HTTP factices démarrés par le test (adresses passées par les variables, voir Q-EVP-06) ; chaque test cite l'id de règle.

- Connexion Google, `GET /google-sign-in/callback` : nominal (compte actif, inscrit, crèche) → `302 /` et cookie de session de 8 h ; signature altérée, mauvais `aud`, mauvais `iss` (les deux formes acceptées), `exp` dépassé (et dans la tolérance de 60 s), `hd` absent / autre, `email_verified` faux, `nonce` différent, `state` invalide ou cookie expiré, algorithme `none`/HS256, clés injoignables, clés avec `kid` inconnu (une seule relecture, puis plus d'une par minute), cache respecté (`max-age`), échange du code refusé, délai dépassé → chacun la redirection attendue sans cookie de session ; compte absent/inactif/sans crèche → `non_autorise` identique ; liaison du `sub` à la première connexion, deuxième connexion par `sub` avec adresse changée, `sub` différent sur compte lié (Q-EVP-05), deux connexions simultanées, `sub` déjà lié à un autre compte ; `sub` absent ou de plus de 255 caractères → `echec` ; `hd` en casse différente accepté ; la liaison est tracée sans `sub` ; aucune sortie (journal du serveur, redirection, audit) ne contient secret, code ou jeton.
- `GET /google-sign-in/start` : `302` avec `hd`, PKCE, `state`, `nonce` et les adresses configurées ; `503` si une variable manque. `GET /service-status` : `google_not_configured`, sans appel sortant.
