# Module evp : plan de réalisation (v3-evp-acces-contrats-siret)

Sources : les quatre demandes à l'API de ce dossier (`google-sign-in-`, `acces-`, `creches-` et `sources-api-modification-request.md`), les plans d'écran, `questions.yaml` et la demande d'origine « v3 : EVP, liaison Google, contrats proposés, professionnelles à plusieurs SIRET, adresses Aqoona réelles ». Le socle est gelé ; tout le code va dans les fonctionnalités EVP non gelées : `google-sign-in/`, `access/`, `creches/`, `sources/`, `evp-core/` (`redact-secrets.ts`). La provenance de chaque règle est reprise telle que la demande la porte (`user`, `inferred`) ; les règles que le backend ajoute pour réaliser une règle amont sont marquées `(inferred, backend)`.

**Une route nouvelle** : `POST /access-accounts/{id}/unlink-google`. Les autres opérations gardent leur chemin et leur déclaration d'accès ; trois réponses changent de forme ou de contenu (`AccessAccountDto`, `GET /creches/{code}/contracts`, libellés de volumes d'Aqoona). Le socle n'est pas touché.

Réponses retenues pour les points ouverts : voir « Questions ». Les décisions du registre `arbitrages.yaml` pour cette version s'appliquent : D-0010 (Q-EVP-13, A, défaut), D-0011 (Q-EVP-11, **B**), D-0012 (Q-EVP-09, A), D-0013 (Q-EVP-10, **B**, précisée par le propriétaire : une salariée ne peut être visible nulle part), D-0014 (Q-EVP-12, A, le propriétaire tenant le cas pour impossible ou pour une même personne avec deux contrats). Les lignes marquées `decision D-xxxx` en sont issues.

## Données

Schéma `base`, `*.tables.ts` de la fonctionnalité concernée. Une migration (`pnpm migrate:gen && pnpm migrate:all`).

- `aqoona_plannings` (`sources/sources.tables.ts`) : ajout `slot_type` text not null, défaut `NON_PRECISE`, contrainte `check (slot_type in ('GARDE','PAUSE','MENAGE','AUTRE','NON_PRECISE'))`. Les lignes existantes prennent `NON_PRECISE` (elles sont remplacées à la lecture suivante). **Aucune colonne ne porte de NIR**, d'empreinte ou de fragment de NIR (`rule-evp-aqoona-nir-never-stored`, user). Index d'unicité du dédoublonnage : `(person_ref, creche_code, company_id, day, start_time, end_time, slot_type)` avec `nulls not distinct` (PostgreSQL 16) ; `rule-evp-aqoona-dedupe` est appliquée en mémoire avant insertion avec **exactement la clé de l'index** (mêmes colonnes, `null` égal à `null`), pour que l'index ne rejette jamais une ligne que la mémoire a gardée ; l'index est la ceinture. Conséquence assumée : deux créneaux non rattachés (sans crèche) de même personne, jour, heures et type collapsent en un. `creche_code` est inclus : une salariée dans deux établissements le même jour à la même heure donne deux lignes (`rule-evp-aqoona-multi-siret-same-day`, user).
- `evp_accounts` (`access/access.tables.ts`) : ajout `session_version` integer not null default 0 (D-0011, `rule-evp-access-session-version`, inferred, backend). Les comptes existants prennent 0 ; un jeton émis avant la migration, sans `sv`, vaut 0. `google_sub` existe depuis la v2. La valeur de `session_version` ne sort jamais de l'API.
- `payfit_*`, `source_anomalies`, `aqoona_mismatches` : inchangés. `payfit_employees` ne reçoit jamais le NIR, même si PayFit le renvoie.
- Rattachement à un périmètre : inchangé (les plannings n'ont pas de périmètre propre ; l'accès passe par les routes existantes).

Notes de réalisation :
- `unlink-google` est ajoutée à `specifications/permissions.yaml` (lecture seule) : voir « Litiges ». `cuisine:routes` doit rendre l'ancien tableau plus cette ligne (`regime: auth`, `allow: [user, admin]`, `action: access:unlink-google`).
- **Édition d'adresse**, dans la transaction de `update()` après les contrôles de droits : (1) si l'adresse normalisée (minuscules, espaces retirés) est égale, sans casse, à l'adresse actuelle, rien n'est écrit pour ce champ ; (2) domaine : même contrôle que `create()` (`422 access.invalid_domain`) ; (3) unicité : `evp_accounts` sans casse (retirés compris) puis violation d'unicité sur `users.email` (`409 access.email_already_exists`, aussi pour une adresse prise par un compte de plateforme hors EVP, sans révéler lequel) ; (4) mise à jour de `evp_accounts.email` et de `users.email` dans la même transaction (`rule-evp-access-address-keeps-link`, inferred). `google_sub`, rôle, état actif, affectations et groupes `evp:<code>` ne bougent pas. Les sessions ouvertes portent l'identifiant du compte et restent valides.
- **Déliement**, dans une transaction avec `lockMemberships` et `for no key update` : `404` si inconnu ; `403 privileged_account` si le rôle n'est pas RO ou DIRECTRICE (y compris pour le superadmin sur son propre accès, option A de Q-EVP-09) ; `403 role_not_manageable` si `manageable(caller)` n'inclut pas le rôle ; `409 google_not_linked` si `google_sub` est nul (aucune écriture, aucune trace) ; sinon `google_sub = null`, `session_version = session_version + 1` (coupe les sessions ouvertes, D-0011) et l'entrée d'audit dans la même transaction (`rule-evp-audit-atomic`). L'ordre des contrôles est celui de `PATCH`. Un accès retiré ou inactif peut être délié comme il peut être modifié aujourd'hui (le comportement de `update()` est conservé).
- **Q-EVP-09, option A** (D-0012) : aucun compte privilégié n'est géré par ces routes ; pas de litige sur `rule-evp-access-no-privileged`.
- **Q-EVP-11, option B** (D-0011) : version de session par compte. `EvpSessionService` inscrit `sv = session_version` du compte dans le jeton au moment de la connexion Google (mêmes claims que l'existant, plus `sv`) ; la garde `CapabilityGuard` compare le `sv` du jeton (absent = 0) à `EvpAccess.sessionVersion` (rendu par `EvpAccessService.load()`, qu'elle appelle déjà) et refuse `401 security.invalid_token` s'ils diffèrent. La comparaison suit `load()` et précède le contrôle de capacité : un compte retiré ou inactif garde son `403` actuel (comportement conservé), un jeton coupé sur un compte actif reçoit `401` même sur une route sans capacité requise. La garde couvre toute route authentifiée EVP, `GET /profile` compris ; si une route gelée du socle y échappe : dispute. Seul `unlinkGoogle()` incrémente la version ; `update()` (adresse, rôle, état, crèches) et le retrait ne la touchent pas, ce qui conserve leur comportement actuel sur les sessions ouvertes. Le jeton d'un compte inexistant ou la lecture impossible de la version est refusé comme un jeton invalide. Aucun autre effet sur l'audit : l'entrée « Liaison Google levée » suffit.
- **Connexion Google** : `resolveAccount()` suit le tableau de la demande. Une seule lecture transactionnelle par `sub` puis par adresse (verrous comme aujourd'hui) ; « admissible » = `usable()` existant (inscrit, actif, non retiré, rôle, au moins une crèche). Cas 2 et 5 n'écrivent rien (ni liaison, ni audit, ni journal) et ne rendent ni adresse, ni `sub`, ni message dans la redirection (`rule-evp-login-mismatch-no-write`, `rule-evp-login-mismatch-no-address`). Cas 3, 6 et 7 : `non_autorise`. La comparaison d'adresse du cas 1 est sans casse (`lower(evp_accounts.email) = identity.email`, `identity.email` déjà en minuscules).
- **Contrats** : `contracts()` ajoute `inArray(payfitContracts.status, ['ACTIVE', 'PENDING'])` aux filtres existants, donc avant la recherche par nom et avant `limit(20)`. Un statut inconnu de PayFit est déjà rangé en `ACTIVE` par `applyPayfit` (`CONTRACT_STATUSES`) : il est proposé. La société de la crèche se retrouve par le SIRET ; le retour anticipé existant (`companies.length !== 1` → `{ items: [] }`) rend aussi `planningRestricted` (calculé comme ci-dessous). **Option B de Q-EVP-10** (D-0013) **avec la précision du propriétaire** (`rule-evp-siret-shared-contracts-visible`, user : une salariée ne peut être visible nulle part) : si le SIRET de la crèche est porté par plusieurs crèches vérifiées du référentiel, `contracts()` ajoute aux mêmes filtres l'exclusion des salariées vues seulement ailleurs, soit `not exists (select 1 from aqoona_plannings p where p.company_id = <société> and p.employee_id = payfit_contracts.employee_id and p.creche_code is not null and p.creche_code <> :code) or exists (select 1 from aqoona_plannings p where p.company_id = <société> and p.employee_id = payfit_contracts.employee_id and p.creche_code = :code)`, avant la recherche par nom et avant `limit(20)` ; `planningRestricted` vaut alors `true`, sinon `false` et rien ne change. Salariée vue à aucune crèche du SIRET, ou Aqoona jamais lue (table vide) → proposée à chaque crèche du SIRET (jamais `items` vide de ce fait). Aucun `not in` sur une colonne nullable (d'où `not exists`). Aucune autre table lue, aucune écriture. Les lignes de `aqoona_plannings` sont celles de la dernière lecture réussie de chaque adresse (`rule-evp-aqoona-partial-failure` : une adresse en échec garde ses créneaux précédents). `POST /absences` n'est pas touché.
- **Lecture Aqoona**, par adresse configurée : (1) `URL` + `dateBegin`/`dateEnd` posés par `URLSearchParams.set` (remplace les valeurs existantes, garde `securityCheck` et tous les autres paramètres tels quels) ; l'adresse complète reste enregistrée comme secret (`registerSecret`) et masquée par `maskUrl` ; (2) réponse = tableau à la racine (`records` = `""`) ; (3) `interpretRecord()` lit `type` (facultatif) et traite `user_matricule` comme valeur transitoire.
- **Rapprochement** dans `applyAqoona()`, pour chaque ligne de la fenêtre : établissement → crèche vérifiée unique (nom normalisé sans espaces, `rule-evp-aqoona-text-normalised`, user) ; société = celle dont le SIRET est celui de la crèche. Si `user_matricule` est un NIR (`canonicalNir`) et que la table de NIR de cette société est disponible : une seule collaboratrice → rattachée, la ligne compte dans « Rapprochés par NIR » ; plusieurs **identifiants de collaboratrice distincts** → non rattachée, détail « Rattachement par NIR ambigu » (décision D-0014 ; le propriétaire tient ce cas pour impossible ou pour une même personne avec deux contrats, qui n'est qu'un identifiant et se rattache), sans repli sur les noms ; aucune → repli sur les noms. Sans NIR, ou table indisponible → noms. Le NIR n'est jamais copié dans une variable qui survit à la boucle : la table de NIR est une variable locale de la lecture, détruite à sa fin ; le nom de la valeur n'entre dans aucune chaîne d'erreur ou de journal.
- `listPayfitNirs` n'est appelé que pour les SIRET qui ont au moins une ligne à NIR valide dans la fenêtre (`rule-evp-aqoona-nir-lazy`, inferred) ; son échec (clé absente, portée absente, 401/403/429/5xx, délai) est converti en anomalie `aqoona_nir_unavailable` (sujet = SIRET) et jamais en échec de la lecture.
- **Plus de 35 clés** : `parsePayfitKeys` accepte déjà 100 entrées ; la lecture reste séquentielle, société par société. Aucun plafond propre à EVP n'est ajouté. Vérifier que la lecture sous 100 sociétés tient dans le délai du flux (aucune limite globale de durée dans `sources.service.ts` à ce jour) ; le test de 40 sociétés factices le prouve.
